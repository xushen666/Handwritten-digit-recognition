# 手写数字识别项目重构设计

- 日期：2026-08-25
- 状态：已由项目所有者确认
- 目标岗位：AI 应用工程师、后端工程师
- 实施时限：一天内完成首个可展示版本

## 1. 背景与现状

原项目是一个课程小组作业，核心实现由仓库所有者主导完成。现有程序使用 PyTorch 训练 CNN，并通过 PyQt5 提供手写画板。原始归档包含源码、模型权重、MNIST 数据、课程报告、IDE 配置、压缩包和大量 PyInstaller 构建产物，但尚未形成可公开维护的 Git 仓库。

现有训练记录的最高测试准确率为 99.71%，但训练脚本使用测试集选择最佳模型。课程报告中的部分功能、性能数字、模型参数量和训练结果也与源码或保存记录不一致。因此，公开版本必须重新建立可复现、可核验的事实基线。

## 2. 目标

首版必须形成以下闭环：

1. 使用固定配置重新训练并正确划分训练集、验证集和测试集。
2. 将模型、预处理和推理封装为唯一的公共核心。
3. 提供 FastAPI 推理服务和最小 Web 手写演示。
4. 保留可离线运行的 PyQt 桌面客户端。
5. 提供快速测试、代码质量检查、Docker 镜像和 Windows 打包流程。
6. 提供中文为主、带英文简介的 README，以及可信的简历项目描述。
7. 让陌生人能够安装、运行、调用、验证并下载桌面成品。

## 3. 明确不做的内容

首版不包含以下功能：

- 在线公开部署；
- ONNX Runtime、量化、剪枝或知识蒸馏；
- 用户纠错、样本数据库或持续训练；
- Grad-CAM、模型切换或复杂可视化；
- 登录、权限、历史记录或任务队列；
- 复杂前端框架、视觉重设计或移动端；
- C++/Qt 重写；
- 多数字、汉字、公式或真实票据 OCR。

## 4. 仓库与模块边界

仓库采用共享核心的 Python 单仓库结构：

```text
Handwritten-digit-recognition/
├─ src/digit_recognizer/
│  ├─ core/          # 模型、预处理、模型加载和推理
│  ├─ api/           # FastAPI 路由、请求校验和响应模型
│  ├─ desktop/       # PyQt 画板和桌面交互
│  └─ web/           # 最小单页手写演示
├─ scripts/          # 训练、评测和指标生成入口
├─ tests/            # 核心、API 和关键交互逻辑测试
├─ models/           # 发布模型和模型元数据
├─ reports/          # 可复现评测结果与图表
├─ docs/             # 截图、接口说明、简历文案和设计规范
├─ .github/workflows/
├─ Dockerfile
├─ pyproject.toml
├─ README.md
└─ LICENSE
```

模型定义、输入预处理和推理只能存在于 `core`。FastAPI 与 PyQt 均调用该模块，不复制算法逻辑。Web 只通过 HTTP 调用 FastAPI。PyQt 直接调用公共核心，因此无需启动服务即可离线运行。

## 5. 数据流

```text
训练脚本 -> 最佳验证集模型 -> 最终测试评测 -> 模型权重与元数据
                                                   |
图片或画板 -> 公共预处理 -> 公共 Predictor --------+
                                |                  |
                                +-> FastAPI -> Web |
                                +-> PyQt 桌面端 ----+
```

训练、评测和应用必须引用同一模型定义及预处理配置。发布模型的元数据记录模型版本、参数量、输入规格、类别、训练配置、评测指标和文件 SHA-256。

## 6. 公共推理核心

公共核心负责：

- 在 CPU 上加载发布模型并切换到推理模式；
- 将 PIL、NumPy 或画板图像转换为单通道 28x28 张量；
- 执行灰度转换、颜色反转、缩放、张量化和标准化；
- 返回预测数字、置信度和单次推理耗时；
- 在模型缺失、文件损坏或结构不匹配时给出明确错误。

空白输入检查属于输入校验，不进入模型推理。所有客户端共用相同判断逻辑。

## 7. FastAPI 与 Web

FastAPI 提供：

- `GET /health`：返回服务状态和模型是否加载；
- `POST /api/v1/predict`：接收 PNG 或 JPEG，返回预测数字、置信度和推理耗时；
- Web 静态页面：由同一服务提供，避免独立前端构建工具。

接口拒绝非图片、超出大小限制、无法解码和空白的输入。客户端错误返回明确的 4xx 响应；服务端错误不泄露本机路径、内部堆栈或敏感环境信息。

Web 页面只包含画板、识别按钮、清除按钮、结果、置信度、耗时和错误提示。

## 8. PyQt 桌面端

桌面端保留现有核心交互：

- 280x280 手写画板；
- 清除和识别按钮；
- 预测数字与置信度展示；
- 空白输入和模型加载错误提示。

桌面端使用正确的控件坐标映射，并直接调用公共推理核心。它不依赖 FastAPI、网络或数据库。Windows Release 采用 PyInstaller 构建并压缩发布；构建缓存和未压缩中间文件不进入 Git。

## 9. 训练与评测

- 运行环境统一为 Python 3.11。
- MNIST 原训练集按固定随机种子拆分为训练集和验证集。
- 训练过程只根据验证集指标选择最佳模型。
- 测试集在模型确定后只进行一次最终评测。
- 沿用现有 CNN、数据增强、Adam 和 15 轮默认训练，不新增模型或大规模调参。
- 新模型最终测试准确率不得低于 99.0%。若未达到，保留真实失败结果并排查原因，不修改或编造指标。

评测生成以下可核验产物：

- 训练和验证损失曲线；
- 训练和验证准确率曲线；
- 最终测试准确率；
- 混淆矩阵；
- CPU 推理耗时中位数和 P95；
- 模型参数量、配置、版本和哈希。

README 只引用本次评测生成的数字，不沿用报告中未经重新验证的参数量、延迟或鲁棒性结论。

## 10. 测试与质量检查

首版测试覆盖：

- 预处理输出的尺寸、通道和数值有效性；
- 空白输入判断；
- 模型加载和推理返回结构；
- FastAPI 健康检查；
- 正常图片、非法文件和空白图片请求；
- 模型元数据和训练配置读取。

CI 使用 `pytest` 和 `ruff`。CI 不下载 MNIST、不重新训练，只执行快速、确定性的测试。测试通过、代码检查通过、API 可启动、Docker 可构建是合并和发布的最低条件。

## 11. Docker、CI 与发布

Docker 只包含 FastAPI、Web、公共核心和 CPU 推理依赖，不包含 PyQt。容器提供健康检查，并支持一条命令启动服务。

GitHub Actions 包含：

1. 推送和拉取请求时运行 `ruff`、`pytest` 与 API 启动检查；
2. 验证 Docker 镜像可构建；
3. 创建版本标签时在 Windows 环境构建 PyQt 客户端，并将压缩包附加到 GitHub Release。

首版交付标准是本地一键运行、Docker 部署后端和 Windows 桌面版 Release。公开在线演示不阻塞首版。

## 12. README 与简历材料

README 开头提供简短英文简介，正文使用中文，包含：

- 项目截图和一句话定位；
- 技术栈与架构；
- 本地、Docker 和桌面版快速启动；
- API 请求与响应示例；
- 训练、评测和测试命令；
- 准确率、混淆矩阵和实测延迟；
- 项目来源、个人贡献和已知局限；
- Release 下载入口。

`docs/resume-project.md` 提供中文简历可直接使用的项目名称、技术栈和三条描述。所有数字来自重构后的产物。项目不得表述为自研 OCR 算法、生产级票据系统或 C++/Qt 项目。

## 13. 隐私、署名与许可证

仓库可以说明项目由课程小组作业重构而来，核心实现与重构由仓库所有者主导。公开仓库不得包含学号、教师信息、组员个人资料或未经同意的个人信息。

以下内容不得提交：

- 原始课程报告和旧 PPT；
- 2.8 GB 源码压缩包；
- MNIST 原始数据；
- `build`、`dist`、IDE 配置、缓存和旧可执行文件；
- 训练设备中的本机路径或环境信息。

仓库采用 MIT License。

## 14. 验收标准

首版完成必须同时满足：

1. 干净环境可按 README 安装项目。
2. 快速测试和代码质量检查全部通过。
3. 训练脚本能够使用固定配置重新生成模型和指标。
4. 新模型测试准确率不低于 99.0%，且指标文件与 README 一致。
5. FastAPI 能处理正常与错误请求，Web 可以完成一次画板识别。
6. PyQt 可以离线完成画板识别并正确处理空白输入。
7. Docker 镜像可以构建并通过健康检查。
8. GitHub Actions 配置有效。
9. Windows 构建产物可以启动，或由标签触发的 Release 工作流成功生成。
10. README、截图、接口说明和简历文案完整且不泄露隐私。

## 15. 一天实施顺序

1. 建立仓库骨架、依赖配置和公共核心。
2. 修正训练与评测流程并启动一次训练。
3. 在训练期间完成 FastAPI、Web 和 PyQt 接入。
4. 补快速测试、代码检查和错误处理。
5. 生成评测产物，回填 README 和简历数字。
6. 构建 Docker 与 Windows 客户端，配置 CI 和 Release。
7. 执行完整验收后提交并推送首版。

如果 Windows Release 因 GitHub Runner 或 PyInstaller 依赖问题未能在当天完成，源码、测试、API、Web、Docker 和打包工作流仍必须完成；该失败必须在仓库中如实记录，不能宣称 Release 已验证。
